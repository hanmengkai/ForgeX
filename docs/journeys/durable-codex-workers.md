# 2.0 持久化 Codex 执行器用户旅程

本轮先接 Codex。需求方提交访客预约需求后，独立 Node Worker 使用本机当前用户登录整理需求；产品与需求方确认后生成设计，研发单独审核设计，通过后才开发与自测。研发审核代码后，另一个执行器通过 HTTP 取得相同摘要的制品，独立测试。测试运维放行隔离测试部署，需求方验收，再经过研发、运维、需求方三方批准，部署到隔离模拟生产环境，三方验收后关闭，保留 Bug 入口。

控制面重启保留需求、审批、异议、任务、通知和 Bug；执行器重启保留领取记录和已签名结果。Codex 登录文件只在执行器设备，控制面只持有执行器公钥及连接令牌摘要。不同执行器使用不同私有目录，禁止借助共享工作目录传递制品。

先验证以下失败场景：

- 控制面重建实例后仍能读到状态；事务失败不留下半次审批，损坏或宽权限状态文件拒绝使用。
- 制品上传不允许跨租户、过期租约、非开发任务、错误输入摘要或错误内容摘要；下载只允许当前任务引用的已审核制品。
- 上传成功但响应丢失可以安全重传；返回内容被改写时拒绝执行，不退回固定模板。
- 执行器被强制停止后不需要手工删锁；同一日志同时启动两个执行器必须失败。
- 完成回执确认丢失、断网和重启只重传同一签名回执；不再次调用模型、测试或发布。
- 中断发生在副作用与落盘之间时只核对现有记录；无法证明完成则阻塞等待人工重试，不猜测成功或再次发布。
- 未经独立设计审核不开发；测试与开发执行器身份分离；三方放行未齐全不部署；已关闭需求仍可提交 Bug。

验收分两类：普通回归使用标明的合成模型响应，但执行真实进程、Git、HTTP 制品传输、业务测试与隔离发布；显式实时验收使用当前用户 Codex 登录并留存模型会话证据。均不连接真实生产。当前本地 SQLite 控制面仅用于隔离样板，生产配置仍使用现有 PostgreSQL。
