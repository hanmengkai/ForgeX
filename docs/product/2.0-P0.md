# ForgeX 2.0 P0：自动化与审批交付闭环

## 用户旅程与完成定义

需求方提交业务目标，由需求 Agent 整理需求方案。产品负责人处理异议并审核，需求方确认具体版本。设计 Agent 产出技术方案，研发进行独立设计审核；审核通过后开发 Agent 实现并由受控工具构建、自测。研发审核交付代码，独立测试执行器验证业务条件，测试负责人确认报告。测试运维执行器部署测试环境，需求方实际验收。

生产运维、研发和需求方分别批准同一个发布候选后，生产执行器部署已验证制品。三方分别确认线上结果，全部确认后需求关闭。关闭后可以提交关联 Bug，并通过新的修复需求完整交付，不覆盖原批准记录。

## 必须成立的规则

- 需求审核、需求方确认、设计审核、代码审核、测试审核、测试环境验收、生产联合放行和线上联合验收是不同关卡。
- 审批绑定阶段轮次及输入摘要；三方关卡要求三个不同自然人，管理员身份不能代替岗位批准。
- 驳回必须有原因；需求变化、设计变化、实现缺陷分别退回对应阶段并使下游批准失效。
- 自动任务必须被具备项目、仓库及阶段能力的受信执行器领取。测试执行器与开发执行器必须独立。
- 任务领取使用租约和隔离令牌；过期执行器不能写入结果。结果签名覆盖任务、输入摘要、令牌和实际输出。
- 自动执行失败显示阻塞，不能填充默认成功。生产重试重新取得三方放行；线上失败先经联合审批恢复，再进入修复。
- 测试、部署和人工验收指向同一代码提交及制品摘要。生产 Agent 不能取得生产凭据和通用 Shell。
- 业务记录、自动任务、批准、通知和幂等请求在同一持久化事务中保存。进程重启不能丢失待办。
- 外部需求方只能读取自己的交付和业务验收信息。通知通过持久化站内待办交付；外部通知适配另行配置。

## P0 执行边界

2.0 使用独立 `/api/v2` 契约和新增迁移，不将旧版 Preview 验收直接等同于线上完成。保留 1.x 入口用于迁移对照。

所有自动阶段通过生命周期执行器消费。需求、设计、开发使用现有隔离 Codex 执行能力；构建、自测、独立测试和环境部署由受控执行适配器完成。执行配置只保存在执行器本地；服务端保存能力和验证公钥，不保存本地模型及环境凭据。

未配置真实模型、业务仓库或部署适配器时，任务保持等待或阻塞。隔离样板验证只能证明对应环境的闭环，不能作为真实客户生产验收。

## 失败验收场景

1. 设计被驳回时，开发任务不能领取。
2. 一个人兼任三种岗位时，不能独自完成联合放行。
3. 修改提交或制品摘要后，旧测试结果和旧批准不能继续使用。
4. 缺少验收条件覆盖或测试失败时，不能部署测试环境。
5. 开发执行器提交独立测试结果、越项目领取、伪造签名、过期回调均失败。
6. 任务响应丢失后重放相同结果幂等成功；相同请求标识携带不同内容拒绝。
7. 需求方测试环境验收通过后仍不能关闭；线上三方确认齐全才关闭。
8. 线上驳回进入恢复审批；恢复执行失败保留阻塞及原因。
9. 原需求关闭后提交 Bug，修复需求保留关联，原需求和证据不被重写。
10. 数据库重启、并发审批和多执行器竞争不能跳过关卡或重复创建任务。
