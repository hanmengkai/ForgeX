# 2.0 持久化控制面与独立 Codex Worker

本轮先支持 Codex，使用当前 macOS 用户的本地登录。需求、审批、异议、任务、通知、Bug 和制品通过本地 SQLite 持久化；四个 Worker 分别运行在独立 Node 进程，使用不同私有目录和签名身份。正式控制面的 PostgreSQL 配置继续保留，本轮不连接真实生产。

## 启动与使用

需要 Node.js 24，当前已验证的 macOS 和已登录的受支持 Codex CLI。初始化过程不复制 Codex 登录文件。执行器配置里的 `execution` 协议为版本 1，显式选择 `provider: codex`、`mode: current_user`；后续后端可扩展此接口，当前不包含 Claude 实现。

在仓库根目录启动控制面：

```bash
npm run p0:durable:console
```

第一次启动会在 `.forgex-local/durable-p0` 建立私有状态、样板仓库和执行器配置。再次启动复用相同账号、执行器身份、数据库和仓库。不要切换目录中的样板模式；离线固定样板使用另一个目录和显式 `FORGEX_SAMPLE_MODE=fixture`。

分别在四个终端启动 Worker：

```bash
node services/device-worker/dist/lifecycle-main.js "$(pwd)/.forgex-local/durable-p0/workers/agent/config.json"
node services/device-worker/dist/lifecycle-main.js "$(pwd)/.forgex-local/durable-p0/workers/test/config.json"
node services/device-worker/dist/lifecycle-main.js "$(pwd)/.forgex-local/durable-p0/workers/staging/config.json"
node services/device-worker/dist/lifecycle-main.js "$(pwd)/.forgex-local/durable-p0/workers/production/config.json"
```

另一个终端运行 `npm run --workspace @forgex/web-console dev`，打开控制台的“完整交付”。六个样板账号分别为 `p0.requester`、`p0.product_owner`、`p0.developer`、`p0.tester`、`p0.test_ops`、`p0.production_ops`，样板密码均为 `P0-Sample-2026!`。样板账号身份固定；浏览器会话是临时的，控制面重启后重新登录。此入口的持久化范围是完整交付流程，其他旧版演示模块及样板账号管理修改不在此持久化范围内。

按页面的下一步提示完成产品审核、需求方确认、独立设计审核、代码人审、测试报告审核、测试验收、三方发布批准和三方线上验收。运维 Worker 执行固定可信部署流程；模型不能获得通用 Shell 或环境发布权限。名称中的“生产”指隔离模拟生产服务，实际目标始终为本机回环地址。

## 制品与恢复规则

- 代码通过 Git 提交后实际执行自测。开发 Worker 上传原始字节、SHA-256 和提交号，控制面确认保存后才接受代码完成回执。
- 测试与部署 Worker 通过 HTTP 下载当前任务引用的同一制品，检查摘要与提交绑定，写入各自私有目录。无需共享源码或制品文件系统。真实 AI 样板还检查可信运行时摘要，并使用 macOS 系统沙箱执行业务函数。
- 上传仅对当前开发任务开放；读取仅对当前任务引用的代码制品开放。请求必须同时匹配执行器、租约、输入摘要及租户、项目、仓库范围。接口版本为 `/api/v2`，传输制品协议版本为 1，大小上限为 128 KiB。
- 每次执行先保存领取日志，返回后保存本地结果及签名回执，再请求控制面确认。确认丢失时只重传相同回执。上传确认丢失时核对已自测的本地制品，补传内容，不重新调用开发 Agent。
- 日志的单实例锁使用 SQLite 的操作系统锁，强制退出后自动释放，不依赖人工删除锁文件。
- 升级已有的旧版文件锁时，必须先停止旧 Worker，再归档旧 `executor.lock`；新版不会绕过仍存在的旧锁启动，防止新旧版本同时执行。
- 样板部署进程独立于 Worker 生命周期。恢复必须同时匹配环境身份、进程启动身份、制品摘要与健康状态；结果缓存丢失时可以核对已落盘的部署回执。停止旧部署也需要这些身份核对。
- 执行中退出且无法核对结果时阻塞。超过租约期限的断网或人工重试造成旧任务失效，也不能拿旧回执替新任务完成。操作人员需要先核对外部副作用，保留旧日志，再通过页面恢复；若旧日志仍待确认，应先停止 Worker，将 `journal/pending.json` 移至同一私有目录下的归档文件，之后再启动。生产模拟发布的重试仍需重新经过三方批准。

停控制面或 Worker 不会删除状态，运维 Worker 停止后隔离部署仍可存活。实时验收脚本会在结束时核对身份并关闭它创建的部署与组件。手动演示结束后，先停止四个 Worker，再运行 `npm run p0:durable:stop`；使用自定义目录时传入 `npm run p0:durable:stop -- /绝对/样板目录`。清理先取得执行器锁，拒绝清理仍在运行的执行器；只停止身份核对通过的隔离服务，保留状态和日志。不要把删除状态目录当作停止部署。

## 自动验收

```bash
npm test
npm run typecheck
npm run test:coverage
npm run p0:durable:verify
```

最后一条会消耗当前用户的 Codex 额度，真实生成需求、设计、代码和独立测试计划。普通测试使用显式标注的合成模型响应，仍执行真实 Git、自测、HTTP 制品交接、业务 HTTP 测试和隔离部署。离线进程验收可运行 `npm run p0:durable:verify -- --fixture`。

独立进程验收注入上传确认丢失、控制面强制停止、发布确认丢失、断网和发布 Worker 强制停止，并核对重启后的部署身份与签名回执。角色审批由测试输入驱动；不代表真人进行了业务验收。证据保存在 `.forgex-local/p0-durable/<时间>/`，该目录包含私有配置，不提交到 Git，不整体分享。

本轮证明同机独立进程与独立目录的 HTTP 协作；真实跨设备网络、Windows/Linux 当前用户沙箱、正式数据库制品适配及真实生产交付仍需后续单独验收。
