# ADR-0004：设备舰队状态使用共享事务仓储

## 状态

已接受。

## 决策

设备登记、在线状态、等待队列、活跃租约、fencing token 和短期幂等墓碑组成一个按租户隔离的舰队聚合。所有读写必须通过 `WorkerFleetRepository.transaction` 完成。

生产环境使用 PostgreSQL 实现：事务开始后按租户取得 advisory lock，再读取并更新舰队 JSON 快照；已完成需求版本另外写入带唯一约束的表，与舰队快照在同一事务提交。唯一范围是租户、项目、需求和需求版本。API 副本不得各自创建独立的生产内存仓储。

`InMemoryWorkerFleetRepository` 只用于测试和明确的单机开发。生产启动前必须执行 `packages/postgres/migrations/0001_worker_fleet.sql`。

## 安全边界

- Control Plane 只向已连接的设备返回一次性可见的原始连接密钥。
- 持久快照只保存连接密钥的 SHA-256 摘要，不保存 Codex 密码、Cookie、OAuth Token 或 API Key。
- Worker 请求同时携带租户范围、设备标识、连接代次和 bearer 密钥；旧代次在重连后立即失效。
- 活跃租约不保存 bearer 密钥，完成墓碑只保留校验幂等所需的最小字段。

## 原因

- 单进程内存无法在重启和横向扩容后维持五账户上限。
- fencing token 必须跨 API 副本保持单调，才能拒绝过期 Worker 的迟到写入。
- 短期墓碑需要有界清理，但“同一需求版本完成后不能重新入队”需要数据库唯一约束长期保证；负责人重新确认的新版本仍可正常交付。

## 后果

- 同一租户的舰队写操作会串行执行；不同租户仍可并行。
- 所有 API 副本必须连接同一 PostgreSQL 数据库，并使用一致的舰队运行参数。
- 修改账户上限、离线时间、租约时间或墓碑策略时，需要显式迁移持久状态，不能让副本静默使用不同配置。
